# Depth checklist（完稿必勾）

复制到回复或草稿顶部，逐项确认：

```
Depth gate:
- [ ] 开场是具体矛盾，不是功能列表
- [ ] 本篇目标有范围边界（不负责什么写清了）
- [ ] §0（或首次出现处）用「是什么→像什么→本项目」解释本篇黑话
- [ ] 「是什么」讲清了层/部件与对外输出
- [ ] 「为什么」有产品或成本动机，不是空喊最佳实践
- [ ] 「优势」相对至少 2 种极端做法
- [ ] 「不做会怎样」反事实表 ≥ 4 行
- [ ] 「原理」有数据流或短路代码，能对上实现
- [ ] 取舍表含「为何不选」
- [ ] 调用链完整，且无仓库路径（用服务名 / 函数名）
- [ ] 核心代码自洽（不依赖私有仓库才能懂）
- [ ] 正文无 `packages/`、`apps/`、`tests/`、`src/foo.ts` 式路径引用
- [ ] 验证步骤用 yarn/公开命令或验收逻辑名，不写测试文件路径
- [ ] 失败/空库/关闭开关等路径写对（已对过代码）
- [ ] 有观测字段或明确写「Phase 未接 metrics」
- [ ] 有可操作验证步骤
- [ ] 有诚实边界（未做 / 经验值 / 已知坑）
- [ ] 语气是复盘，无面试/简历/口述措辞
- [ ] 无编造的性能数字；有数字则带来源或实测说明
- [ ] 系列导航与上下篇链接正确（若适用）
```

## 常见深度不足（返工信号）

| 症状                        | 补什么                         |
| --------------------------- | ------------------------------ |
| 只有「我们用了 X」          | 加为什么 / 不做会怎样          |
| 代码只有函数名              | 贴完整控制流                   |
| 「详见仓库」/ 甩 `apps/...` | 内联实现；改成函数名 / 服务名  |
| BM25/RRF 等缩写裸奔         | §0 三句话解释                  |
| 验证写 `tests/.../*.ts`     | 改 `yarn …` 或「某 Wave 验收」 |
| 边界写成「未来可扩展」      | 改成「现在没做 + 后果」        |
| 阈值/开关含糊               | 写默认值与 env 名              |
| 空库/失败路径靠猜           | 回源码确认 probed/skip/throw   |
